# vtimidiports — Windows MIDI ports for the Virus TI

Option A of [`findings/design-midi-ports.md`](../../findings/design-midi-ports.md). Gives Windows programs the two
MIDI ports the old Access driver had, with no driver:

| Port | USB-MIDI cable on MI_03 | What it is |
|---|---|---|
| **Virus TI Synth (Revive)** | 1 | The synth engine: the Virus keys and knobs come in here; notes sent here play it. |
| **Virus TI MIDI (Revive)** | 0 | The Virus 5-pin MIDI In/Out sockets (the Virus as a MIDI interface). |

It is a broker client (`vtiproto.h`): EP 0x85 packets are split by cable and sent to the ports as UMP; port output
is packed into USB-MIDI packets and written to EP 0x05. The plug-in's channel (MI_04, cables 2/3) is not touched, so
the ports and the plug-in work at the same time. Active Sensing (FE) is not forwarded.

## Requirements

- Windows 11 with Windows MIDI Services in the box (the `midisrv` service and
  `System32\Midi2.VirtualMidiTransport.dll`). Tested on 26H2 (MidiSrv 10.0.26100.7705, virtual transport 1.0.15).
- Nothing to install for the user. The `Windows.Devices.Midi2` API is app-local: it ships next to the exe from the
  preview NuGet package (see Build) until Microsoft puts it in the box.

## Build

The API package is published on GitHub, not on nuget.org:

```
gh release download inbox-preview-11 -R microsoft/MIDI -p "Windows.Devices.Midi2.*.nupkg" -D src/midiports/packages
dotnet build src/midiports -c Release
```

The C# projection is generated by CsWinRT from this machine's Windows metadata (`CsWinRTWindowsMetadata=local`), so no
Windows SDK install is needed. The older `Microsoft.MIDI.SDK` 1.0.16-rc.3.7 "Runtime and Tools" installer is gone
from GitHub (winget fails with 404) and is not needed.

## Use

- Run `vtimidiports.exe`. It waits for the broker (which starts on demand) and reconnects by itself.
- Stop it with **`vtimidiports.exe --quit`**. Only one instance runs at a time.
- Log: `%TEMP%\vtimidiports.log`.
- In Ableton Live: *Settings → Tempo & MIDI → Input Ports*, turn **Track** on for "Virus TI Synth (Revive)", then set
  the Virus track's *MIDI From* to it. Leave **Track off for the output port** of the same name: the plug-in already
  sends the track's notes to the synth, so the output port would double them.

## Known problems

- **Never kill the process.** A killed `vtimidiports` leaves its virtual devices registered, and the Windows MIDI
  Service then hangs in `MidiSession.Create` for every program until `midisrv` is restarted. `Restart-Service midisrv`
  itself hangs in *stop pending*; what works (elevated):
  `Stop-Process -Name MidiSrv -Force; Start-Service midisrv`. Seen three times on 2026-10-14.
- Disposing the MIDI session after the ports were disconnected also hung (the ports were already gone), so `--quit`
  exits straight after the disconnects. Even so, one `--quit` was followed by a service hang once the process was
  killed. Until this is understood: start it once (at logon) and leave it running; Windows shuts it down at logoff.
- Right after `midisrv` starts, `CreateVirtualDevice` can return null; the program retries five times, 2 s apart.
- Windows names a virtual device's MIDI 1.0 ports `<device>`, `<device> Gr 2`, ... ("classic" naming) and refused a
  runtime custom port name (`MidiServiceEndpointCustomizationConfig` → `ErrorFromService`). That is why there are two
  virtual devices with one group each instead of one device with two function blocks.

## Measured

- Keys while the plug-in is open: note on/off and channel pressure arrive on EP 0x85 cable 1; knobs come on EP 0x86
  cable 2 (the plug-in's channel), so they are not on these ports.
- Latency through the ports is not measured yet.
